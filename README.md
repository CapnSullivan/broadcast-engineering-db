# Broadcast Engineering SQLite Database

Учебно-инженерная модель оборудования и кабельных соединений телевизионной аппаратной на SQLite.

Репозиторий демонстрирует **структуру данных и SQL-логику**. Исходная рабочая база, реальные кабельные журналы, расположение оборудования и идентификаторы не публикуются. Данные в `demo.sql` полностью вымышленные.

## Что реализовано

- Каталог моделей оборудования и портов: `models`, `model_ports`.
- Экземпляры устройств с привязкой к модели: `devices`.
- Кабельные соединения и их конечные точки: `cables`.
- SQL-представления для просмотра направленных связей, кабельного журнала, свободных портов и неполных соединений: `edges_flow_v`, `journal_design_v`, `ports_unused_v`, `open_ends_v`.
- Модель нормальной коммутации jackfield: `vjp_normals`, `vjp_design_v`.
- Учёт оперативных коммутаций и программных наложений: `vjp_live_patches`, `vjp_program_patches`, `vjp_current_status_v`, `journal_live_v`.

SQL-представления вычисляют состояние на основании записей; приложение с пользовательским интерфейсом в репозиторий **не входит**.

## Быстрый запуск

Нужен только **SQLite 3** (например, `sqlite3` CLI или DB Browser for SQLite / DBeaver с поддержкой SQLite).

Из корня репозитория:

```bash
sqlite3 demo.sqlite ".read schema.sql"
sqlite3 demo.sqlite ".read demo.sql"
sqlite3 demo.sqlite "SELECT vjp_device, a_port, b_port, status_source, current_state FROM vjp_current_status_v;"
```

Ожидается две строки: первая с источником `LIVE` и состоянием `BROKEN_AT_A`, вторая с источником `DEMO_PROGRAM` и состоянием `BROKEN_AT_B`.

Файл `demo.sqlite` создаётся локально, в Git не загружается. Для запуска через DBeaver можно создать новую пустую SQLite-базу и последовательно выполнить `schema.sql` и `demo.sql`.

## Примеры запросов

```sql
-- Журнал проектных соединений
SELECT cable_label, src_device, src_port, dst_device, dst_port
FROM journal_design_v;

-- Статусы jackfield с учётом оперативных патчей и программы
SELECT vjp_device, a_port, b_port, status_source, current_state
FROM vjp_current_status_v;

-- Направления и статусы определения сигналов
SELECT cable_label, from_ref, to_ref, direction_status
FROM edges_flow_v;

-- Незадействованные порты
SELECT device_id, doc_name, io, domain FROM ports_unused_v;
```

## Архитектурные замечания и ограничения

- `DESIGN` хранит базовую схему кабельной разводки, а `LIVE` и `PROGRAM` описывают наложения для коммутации. Это логическая модель, не система автоматического управления аппаратной.
- `cables` допускает неполные и внешние окончания без полноценной записи в `devices`; внешние конечные точки не обязательно означают ошибку. Из-за этого для концов кабеля не задан внешний ключ на `devices`.
- Направление потока в `edges_flow_v` выводится из `io`; если его нельзя уверенно установить, состояние `UNKNOWN`. Физическая доступность сигнала не проверяется.
- В схеме представлений есть специальные правила для `VJP.model` и обозначений портов `A...` / `B...`; это предметная логика, а не универсальный graph engine.
- `schema.sql` сохранён из текущей БД; исправлена одна устаревшая ссылка внешнего ключа `aliases` с `devices_old` на `devices`. Рабочий файл базы не изменялся.
- Результаты SQL не заменяют реальную проверку коммутации. Утверждений о производственной готовности нет.

## Тесты

```bash
python -m unittest discover -s tests -v
```

Тест создаёт **временную базу в памяти**, применяет схему и вымышленные данные и проверяет целостность и ключевые представления. Python нужен только для теста.

## Публикация

В репозиторий включены `schema.sql`, `demo.sql`, тесты и документация. Реальная база намеренно исключена. Не публикуйте внутренние кабельные схемы и фактические идентификаторы без разрешения владельца инфраструктуры.
